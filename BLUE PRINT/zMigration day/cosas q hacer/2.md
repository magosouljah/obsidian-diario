No es realista eliminar todos los errores, pero sí puedes hacer que sean mucho menos frecuentes, más pequeños y fáciles de diagnosticar. En este proyecto, lo más importante es fortalecer los límites entre Desktop, Rust, helpers, Cloud y Telegram.

## Prioridades para BeatVault

1. **Validar contratos entre librerías**

El error ocurrió porque dos APIs tenían métodos llamados `read`, pero contratos incompatibles. Conviene encapsular cada librería externa detrás de adaptadores propios:

```
function createTelegramUploadStream(filePath) {
  const nodeStream = fs.createReadStream(filePath);
  return {
    nodeStream,
    webStream: Readable.toWeb(nodeStream),
  };
}
```

El resto de la aplicación sólo usa ese adaptador. Si `mtcute` cambia, hay un único punto que revisar.

2. **Ninguna operación externa sin timeout**

Toda operación de red, proceso hijo, lectura de `stdout`, conversión multimedia o acceso a disco debería tener:

- Timeout explícito.
- Cancelación.
- Limpieza en `finally`.
- Error que indique operación y etapa.
- Reintento únicamente cuando sea seguro.

Esto evita que un error se transforme en una aplicación congelada.

3. **Máquinas de estados con estados terminales**

Cada carga debería terminar obligatoriamente en uno de estos estados:

```
queued → preparing → uploading → committing → completed
                                      ↘ failed
                                      ↘ cancelled
```

No debe existir un camino que abandone la función dejando `uploading` activo. Un bloque `finally` debe limpiar cola, journal, referencias y operación Cloud.

4. **Pruebas contra las interfaces reales**

Los mocks no habrían detectado este problema si aceptaban cualquier stream. Añadiría pruebas de integración que usen:

- Un MP3 real pequeño.
- El helper generado real.
- El protocolo stdin/stdout real.
- Un servidor o transporte controlado.
- Un cierre de aplicación durante una carga.
- Un transporte que nunca responde.
- Un transporte que responde tarde o devuelve datos inválidos.

Una prueba específica debe verificar que el stream entregado a `@mtcute/web` sea un `ReadableStream` Web, no un `fs.ReadStream`.

5. **Watchdog de operaciones**

Registrar cada operación activa con:

- `operation_id`.
- Sesión y helper PID.
- Etapa actual.
- Inicio y último progreso.
- Bytes procesados.
- Deadline.

Si deja de progresar, el watchdog cancela la operación, termina el helper y libera el pool. La interfaz puede mostrar: “La carga se detuvo durante `sendMedia` después de 60 segundos”.

6. **Logs estructurados y correlacionados**

Usar el mismo identificador desde el clic en Save hasta Telegram:

```
beat_id
operation_id
session_id
helper_pid
topic_id
message_id
stage
elapsed_ms
```

Registrar `START`, `OK` y `ERROR` para cada etapa. Evitar logs que puedan contener tokens, claves o credenciales.

7. **Control estricto de procesos hijos**

Cada helper debe:

- Pertenecer a una instancia concreta de la app.
- Detectar el cierre de stdin.
- Recibir cancelación.
- Tener deadline.
- Ser terminado y recolectado con `wait()`.
- No impedir el cierre de la aplicación.
- Poder ser reemplazado después de un fallo.

También conviene una prueba automática que cierre la app durante una carga bloqueada y confirme que no queda ningún helper huérfano.

8. **Fuente y bundle generado siempre sincronizados**

Actualmente existen `transport-helper.source.mjs` y `transport-helper.cjs`. En CI debería ejecutarse:

```
generar bundle
git diff --exit-code transport-helper.cjs
```

Así una modificación de la fuente nunca se entrega con un bundle antiguo.

9. **Puertas obligatorias antes de integrar cambios**

Como mínimo:

```
format/lint
typecheck
pruebas unitarias
pruebas de integración
cargo check
regresiones Direct
verificación del bundle generado
git diff --check
```

El cambio no se integra si falla cualquiera. Para cargas y almacenamiento, añadiría además una prueba real controlada en un entorno de staging.

10. **Actualizar dependencias de forma controlada**

No actualizar muchas dependencias juntas. Usar cambios pequeños y comprobar especialmente:

- Streams.
- Abort/cancelación.
- APIs de subida y descarga.
- Tauri y WebView.
- Serialización Rust/JavaScript.
- Manejo de procesos Node.

Fijar versiones mediante el lockfile y revisar las notas de cada actualización.

11. **Separar los fallos recuperables**

Una carga fallida no debería congelar toda la cola. Debe poder:

- Marcar sólo ese beat como fallido.
- Conservar información suficiente para reintentar.
- Continuar con el siguiente.
- Evitar duplicar un MASTER o una entrada INDEX.
- Reconciliar journal, Telegram e INDEX después de reiniciar.

12. **Revisiones centradas en modos de fallo**

Para cada cambio importante, responder antes de aprobarlo:

- ¿Qué pasa si nunca responde?
- ¿Qué pasa si el proceso muere?
- ¿Qué pasa si se cierra la app?
- ¿Qué pasa si se corta internet después de subir pero antes de actualizar INDEX?
- ¿Puede duplicarse la operación al reintentar?
- ¿Se libera siempre el mutex?
- ¿Se limpian siempre journal, pool y referencias?

## Lo que implementaría primero

En orden de impacto:

1. Prueba de integración del helper con stream real.
2. Prueba de timeout y helper huérfano.
3. Estado de operación con etapa y último progreso.
4. Verificación automática de fuente contra bundle.
5. Pruebas de cierre durante carga.
6. Reconciliación automática de journal e INDEX al iniciar.
7. Pipeline obligatorio de validación antes de integrar cambios.

La idea central es esta: **cada operación externa debe poder terminar correctamente, fallar con información útil o cancelarse; nunca quedarse esperando indefinidamente**. Esa disciplina habría prevenido tanto el bloqueo de la carga como los procesos huérfanos.
